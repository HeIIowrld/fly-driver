# 실제 회전 피드백 제거 비교 — 효과 미입증, 입력 시간 불일치

2026-10-29, Asia/Seoul. [프로젝트 대전제](PROJECT_CHARTER.md)는 그대로다.
**실제 차량에 full과 yaw0 조건을 각각 적용하고 두 에피소드 전체를 원본 재생으로 검증했다.
그러나 교란 지속시간이 달라 유효 비교 조건을 통과하지 못했다. 실제 안정화 개선은 미입증이다.**
이 결과로 후보 t1121을 승격하거나 기전/주행/랩타임 목표를 완료로 표시하지 않는다.

## 시험 경계와 사전 계획

`configs/flight-physical-yaw-perturbation-v1-20261029.json`에 세 블록12회, 양방향 교란,
full/yaw0 순서와 평가 조건을 고정했다. 시험용6km/h 페달, 조향 의도×−0.6/±0.1 제한은 유지했다.
추가 교란은 조향 요청에 ±0.05를 더하고 최종 ±0.1로 제한한다. 정답 경로·지도·world pose는
actor에 넣지 않으며 위치/기어/이탈은 별도 진단 가드만 사용한다.

- `full`: 등록된 실제 몸 yaw를 원래 비행 감각 경계에 넣는다.
- `zero_yaw`: 그 경계의 yaw 값만0으로 바꾼다. 원본 센서값·유효성과 다른 몸 감각은 보존한다.
- 모델 가중치·원본 연결·readout·영상 입력을 바꾸지 않는다. 새 에피소드마다 상태를 초기화하고
  정차→출발→baseline→교란→복원→제동257관측을 끊김 없이 유지한다.
- 새로운 경계 코드는 `flight_yaw_trial.py`다. t1160은 이전 실제225관측 전부를 두 모드의
  독립 프로세스로 재생해 full 최대9.69e-8/yaw0 최대1.83e-7의 대조 오차를 확인했다.
  초기 t1159는 같은 프로세스의 두 번째 datamate 호환 처리 때문에 실패했고 원본을 보존했다.

IAE는 교란 직전0.3초의 실제 yaw 평균을 기준으로, 실제 독립 native 표본만 적분했다.
교란 종료 뒤1.6초까지 관측하며 샘플 보간·공백 삭제·새 시각 생성은 하지 않았다.
시각은 host driver 호출 완료 경계다. 엔진의 정확한 적용 시각이나 simulation clock으로 바꾸어 부르지 않는다.

시작 위치 차이0.000186m, baseline 속도 차이0.08070km/h, yaw 차이1.47e-5rad/s는 조건 안이다.
하지만 **교란 지속시간 차이26.064ms는 허용10ms를 넘었다.** 입력 크기/시간이 다르므로 raw IAE의
full−yaw0 차이를 안정화 향상이나 악화로 해석하지 않는다. 결과를 본 뒤 입력 시간으로 나누어
통과 판정을 만들지도 않는다. 회복 관측 약0.263/0.260초도 같은 이유로 우열을 판정하지 않는다.

시간 일치 조건은 첫 full의 시간 측정 후, 첫 완료 yaw0 교란을 보기 전에 추가했다.
[추가 시점과 이유](flight-physical-yaw-timing-amendment-20261029.md)를 별도로 보존했다.
원래 계획의 일부였다고 소급 주장하지 않는다. 계획한12회 중 완료2회/3블록 미완료다.
현재 v1을 맹목적으로 이어서 성공 사례를 고르지 않는다. 입력 시간을 제어하는 새 프로토콜이 필요하다.

중단 기록을 잘라 학습하거나 에피소드 중간 상태를 초기화해 재사용하지 않았다.
재시도는 항상 명시적 API restart/start와 새 신경 에피소드였으며, 완료한 독립 시험은 원래 경로/해시로
참조했다. 실패 데이터와 로컬 원본 로그/NAS 복사를 모두 보존했다. 실패도 실제 실행 수에 포함한다.

`FileTelemetryClient.snapshot`과 새 `ac_published_state.py`는 Windows producer 읽기 충돌만 최대10ms
재시도한다. 같은 패킷의 원래 수신 시각과 bytes를 유지하고, 오래된 값으로 대체하지 않는다.
CSP 상태는 같은 열린 파일의 수정 시각으로 신선도를 검사한다. lifecycle 읽기도 같은 처리를 쓴다.
정리 제동은 낮은 속도 한 표본이 아니라 연속5표본의 brake hold를 확인한다.
t1164에서는 첫 낮은 속도 뒤 반동이 보여 최종 pause 확인이 실패했고, 새 독립 정차 관측 뒤
t1165 API pause를 따로 완료했다. 이 실패를 원래 실행의 성공으로 덮어쓰지 않았다.

## 지연 진단 — GC로 단정하지 않음

- t1167 읽기 전용200회 검사에서 NAS stop stat/창 확인/프로필 해시/native AI/CSP JSON을 합한
  가드 중앙값1.00ms/최대2.70ms였다. 이것만으로 실제 동시 부하의 모든 지연 원인을 배제하지 않는다.
- t1168의 가드·수신·신경 추론·GC 시각을 로컬 원본에 추가했다.
  마지막 실패의 첫 세 추론은13.64/71.49/96.20ms였다. 다음 실제 관측 간격이99.45ms가 됐다.
  해당 가드는 약1ms, 전송 전 native/진단 수신은 약0.3ms였다.
- 긴 계산으로 다음 관측 간격이 늘고, 그 원래 시간을 적분할 내부 tick이 늘어 다시 계산이 길어지는
  연쇄를 확인했다. 최초의 계산 지연 원인 자체는 아직 확정하지 않았다.
- 큰104ms GC 이벤트는 준비 단계에 있었다. 마지막 실패의 실제 관측 구간 GC는 약0.094ms였다.
  따라서 이 실패를 GC가 원인이라고 주장하거나 근거 없이 GC를 꺼서 해결됐다고 하지 않는다.
- 최악 시간의 scratch 준비·GPU 운영/동시 부하를 더 검증해야 한다. 80ms/150ms 가드는 유지한다.

새 파일/패킷/명령 가드 관련20검사와 기존 lifecycle143검사를 통과했다. 실제 완주·기전 전체의
성공을 뜻하지 않는다. AMD 진단 help는 LoadLibrary 접근 오류로 끝났고 성능 근거에 사용하지 않았다.
