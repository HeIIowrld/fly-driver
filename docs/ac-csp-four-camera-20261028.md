# AC 엔진의 독립 카메라 네 개

2026-10-28 KST. 이전에는 기본 화면의 전방 crop과 가상 미러 crop까지만 확인했다.
이번에는 공식 CSP 0.2.11을 설치하고 엔진에서 대시 전방·좌·우·후방을 각각 렌더링했다.
아래 설치·초기 실측은 학생 제어와 분리한 읽기 전용 계측이다. 이후 네 카메라의 모델
연결·학습·짧은 제어 시험까지 진행했으며, 최신 상태는 다음 절에 구분한다. 자율 완주는 아직 없다.

후속 학습·실제 주행 실패와 개선 근거는 [학생 제어 기록](ac-csp-student-control-20261028.md)을
따른다. 최신 t202 모델도 지속 출발과15m 목표를 달성하지 못했다.

## 현재 적용한 구성과 후속 검증

사용자 요청대로 전방은 차량 기본 대시 카메라 위치를 사용한다. 좌·우·후방은 CSP의
`ac.GeometryShot`으로 엔진 장면에서 각각 렌더링한다. 화면 전환이나 데스크톱 crop으로
만드는 영상이 아니므로 게임을 앞에 띄우고 시점을 번갈아 바꿀 필요가 없다. 게임의 렌더
프로세스는 계속 실행돼야 한다. 거울을 통과한 반사 영상 대신 방향별 외부 카메라를 사용한다.

실제 네 방향 미리보기는 아래 이미지다. 각 소스는 320×180이며 전방 수직 화각은 약56°,
나머지는 약90°다. 좌우 카메라는 측면을 향하므로 전방 사각까지 빈틈없이 덮는 360° 광학계로
검증된 구성은 아니다. 앞쪽 측면의 연속 커버리지가 필요하면 좌우 방향을 비스듬히 돌리고
투영·망막 등록을 갱신한 뒤 다시 학습·평가해야 한다.

네 영상을 하나로 이어 붙이지 않고 소스별 1,709개 수용기로 변환해 몸 기준 시선 방향과
함께 신경회로에 입력한다. 소스별 영상 나이와 결측을 별도로 처리하며 몸 감각을 함께 넣는다.
현재 계약은 `configs/ac-csp-retina.json`, 구현은 `src/flybrain_drive/ac_csp_retina.py`다.

- t162는 실제 교사 제어 200개 관측의 영상·몸 입력과 행동을 재생 검증해 학습 자료로 봉인했다.
  t168의 별도75개 관측은 개발 평가에 사용했다.
- t164에서 네 카메라 학생을 학습했고 t175에서는 백그라운드에서75회 읽기 전용 추론을 했다.
  카메라·센서 수신 시계는 QPC로 통일했다. PNG/JSON 기반 전달이며 GPU 공유 텍스처 소비는
  여전히 미구현이다.
- t176/t177에서 학생 출력8개를 실제 제어에 전달했고 약0.269m 변위, 최대약5.002km/h 뒤
  설정한 속도 제한으로 정지했다. 입력과 출력 재생 오차는0이었으나 경로 추종 성공은 아니다.
- t169의 개발 평가에서는 조향 편향이 남았다. 네 카메라가 전방만 쓴 경우보다 우수하다는
  비교 실험, 물리적으로 동시인 노출 검증, 서킷 완주는 아직 없다.

엔진 확인 근거는 각 run의 카메라별 PNG와 반환 시선·위치·투영행렬이다. 아래의 초기
미연결 목록은 t144~t151 당시 상태를 기록한 것으로, 현재 모델 연결 여부는 이 절을 따른다.

## 설치와 복구 근거

공식 권장 버전은 [배포 페이지](https://acstuff.club/patch/)에서 확인했다. 공식 다운로드는
`https://acstuff.club/patch/?get=0.2.11`이며 ZIP SHA-256은
`0729ccaebb403a7a6d1c40516990da8116cb5f56eea4c1fe0bdd29863a5a6ffb`다.
압축 CRC와 복사 파일 해시를 검사했다. 기존 `acs.exe`를 변경하지 않고 새 `dwrite.dll`,
`extension/`, 프로젝트 카메라 앱을 배치했다. 설치 당시697개 파일과 해시는 t140에 있다.
DLL 서명자는 AcClub이며 자체 서명 체인으로, Windows 신뢰 체인 검증 성공으로 보고하지 않는다.

기존 사용자 cfg는 다음 로컬 디렉터리에 복사 보존했다.
`C:/Users/jeff4/AppData/Local/flybrain-review-20261027/csp-0.2.11/backup-before-install/user-cfg/`.
ZIP과 staging도 같은 상위 디렉터리에 보존했다. 복구 시 t140에 기록된 새 파일만 대상으로
해야 하며, 다른 게임 파일을 재귀 삭제하는 방식으로 복구하지 않는다. CSP 실행 뒤 생긴
사용자 설정 변경은 백업과 비교해야 한다. 현재 카메라 Lua는 설치 초기 버전에서 수정됐고
t144에는 실제 사용한 소스 사본과 해시가 있다.

실제 프로세스 모듈에 게임 디렉터리의 DWrite.dll이 로드됐고 앱 응답에서 버전0.2.11,
버전 코드3465를 확인했다. 재실행마다 이전 세션의 조향 보정은 다시 검증해야 한다.

## 구현과 실측

`integrations/ac_csp/FlyBrainCamera/`는 LAZY=NONE인 Lua 앱이다. 요청이 없으면 대기하며,
현재 요청 ID별1~1000묶음,0.03~2초 주기,최대60초의 제한을 검사한다. 요청 디렉터리 재사용은
거부한다. 모든 요청은 조향·페달·AI·물리 변경 없이 영상만 출력한다. 각 묶음에 요청 ID,
렌더 프레임 번호, 카메라 ID, 시선·위치·투영행렬, 스크립트 시각을 기록한다. 월드 위치는
렌더러 내부와 진단 메타데이터에만 있으며 actor 입력으로 연결하지 않았다.

| 소스 | 렌더 위치·방향 | 반환 투영행렬의 수직/수평 화각 |
|---|---|---|
| front | 차량 `dash_cam.ini`의 POS, 전방 | 약56° /86.78° |
| left | 차체 왼쪽1.15,높이1.0의 외부 시점 | 약90° /121.28° |
| right | 차체 오른쪽1.15,높이1.0의 외부 시점 | 약90° /121.28° |
| rear | 차체 뒤2.4,높이1.0의 외부 시점 | 약90° /121.28° |

모든 이미지는320×180이다. POS 값은 해당 차량 기본 설정에서 읽고, 좌우/후방 위치는
선언한 공학적 오프셋이다. SI·실물 광학 보정을 독립적으로 마친 수치라고 하지 않는다.
좌우/후방은 실제 거울 영상이 아니라 방향별 외부 카메라다.

초기 t141은 HDR→LDR 변환이 빠져 어두웠다. t142는 YEBIS 변환을 넣었고, t143은
노출0.35를 명시했다. 영상 검토에서 좌우가 뒤집힌 것을 발견했다. BMW 모델 +X가
운전자 왼쪽이라는 점을 대시 좌석 위치와 화면의 관중석·펜스로 확인해 수정했다.
초기 세 run은 최종 카메라 설정이나 학습 자료로 사용하지 않는다.

수정한 t144는 백그라운드에서8묶음·32장, 요청 주기0.1초로 완료했다. 시작·종료 시 게임은
전면이 아니었고, 수집 중 UI/구동기 요청은0이었다. 모든 파일 복사 해시·카메라 ID·크기·
렌더 프레임 증가를 검사했다. 이미지는 단색이 아니며 직접 검토했다. 차가 정차해 있으므로
픽셀 차이만으로 움직이는 장면의 지연을 검증한 것은 아니다.

t145는8묶음의 반환 행렬을 검사했다. 회전 직교성, 요청한 카메라 원점과 시선, 화면 오른쪽
축에 대한 좌/우 부호, 후방의 반대 방향, 종횡비와 수직 화각이 맞았다. t146의 의도적인
과거 좌우 오류 자료 감사는 같은 검사에서 실패했다. 이것은 반환된 엔진 행렬과 요청값의
일관성 검사이며, 실물 광학이나 물리적 동시 노출 검증과 구별한다.

첫 묶음을 제외한 t144의 카메라별 렌더 호출~PNG 저장 시간은 중앙값4.39ms,
95백분위4.92ms였다. GPU 실행만의 시간이 아니고, 전체 수신·전처리·추론·제어 지연도
포함하지 않는다. 네 소스를 저장하는 시간과 초기 YEBIS 준비 비용도 있으므로25Hz 제어를
달성했다고 해석하지 않는다.

## 백그라운드 부하 제한

처음에는 창을 뒤로 보내도 메인 렌더가 약598FPS로 돌아갔다. 공식 패키지
`extension/config/dxgi_tweaks.ini`의 설명에 따라 사용자 설정 파일의
`[COMMON] BACKGROUND_PAUSE=2`를 적용했다. 이 옵션은 백그라운드30FPS를 뜻한다.
실행 중 변경만으로는 약578FPS라 t148에서는 적용 성공으로 판정하지 않았다.

게임을 한 번 재실행한 후 t150에서는 실제 렌더 프레임 번호/스크립트 시각으로 약30.29FPS를
측정했다. t149는 그 상태에서 네 카메라8묶음·32장을 다시 수신했고 시작·종료 모두
비전면이었다. t151의 행렬·파일 감사도 통과했다. 별도의 조향·가속 요청은0이다.
이는 렌더 빈도 제한의 확인이며 GPU 전력·활용률 감소량을 직접 측정한 결과는 아니다.
또한 기존 물리 시뮬레이션 속도나 자율주행 성능이 개선됐다는 뜻도 아니다.

현재 game PID/센서 producer는 첫 설치 시험(t147) 뒤 다시 바뀌었으므로 최신 세션은
t149 manifest와 t150의 추가 런타임 기록을 따른다. 과거 producer에 대한 보정으로
새 세션에서 주행을 시작하지 않는다. 기본 창이320×180으로 달라져 이전 전체창 crop
설정도 현재 창에는 맞지 않는다. 새 엔진 카메라 입력 계약을 만들기 전 학생 창 캡처
추론은 `ac-live-view-contract.json`에서 차단했다.

## 초기 계측 당시 미연결 부분 (t144~t151)

- `sharedHandle(true)`는 기록했지만 수집 종료 시 텍스처를 해제하므로 과거 handle은 재사용할
  수 없다. 다른 프로세스가 공유 텍스처를 실제 읽는 부분은 미구현이다.
- 현재 Python 수집기는 PNG와 JSON을 해시 검증해 보존한다. 실시간 actor 입력, 몸 감각과의
  시각 정렬, 네 소스별 나이·결측 처리와 재귀 상태 연결은 다음 단계다.
- 현재 데이터는 `training_admissible=false`, `actor_stream_created=false`다. 노출 시각의
  물리 보정과 새 카메라용 학습·실제 주행은 아직 없다. 기존 창 crop 망막 계약을 재사용하지 않는다.
- CSP 자체가 게임의 렌더·설정 동작을 바꾸므로 세션/프로필/센서/조향을 다시 확인한 뒤
  주행 제어를 재개한다. 기존 학생의 가속 유지 실패도 아직 해결되지 않았다.

다음은 파일 저장을 줄인 유한 스트림과 센서 수신을 묶고, 카메라별 실제 행렬로 망막 입력을
등록하는 작업이다. 그 뒤 새 관측의 교사 질의와 학습, 저속 연속 주행으로 이어간다.
코너·제동, 타이어 온도·하중·셋업 적응, 자율 완주와 랩타임 최적화는 전체 목표로 남아 있다.
